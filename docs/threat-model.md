# Threat model

## Assets to protect

- host filesystem outside the selected workspace;
- SSH keys, GitHub credentials, cloud credentials, API keys, browser/session data, and agent authentication state;
- the Docker daemon and other privileged host services;
- CI or maintainer repository write permissions;
- integrity of evidence generated by ReproForge.

## Adversaries and untrusted input

Assume a repository, dependency, test, build script, issue body, fixture, generated file, and agent-produced command can be malicious. An issue may contain prompt injection intended to persuade a harness to expose credentials, enable networking, rewrite evidence, or push code.

## Trust boundaries

### Host/control plane

The control plane may hold GitHub credentials for issue metadata or comments. Those credentials are not inherited by sandbox processes. Host-side Git may use the operator's configured credential helper to clone a private repository, but the resulting credential material is not mounted into the execution container.

### Project sandbox

Only the target workspace is bind-mounted read/write. Container root is read-only by default; `/tmp` is a tmpfs and becomes `HOME`. Linux capabilities are dropped, `no-new-privileges` is set, resources are bounded, and network mode defaults to `none`.

The workspace is not a confidentiality boundary. Malicious code can read and modify anything in that workspace.

### Harness sandbox

Harnesses run in a separate disposable container that shares the workspace. This limits host exposure, not mutual trust between the harness and target repository. The target repository may attempt to influence the agent through files, instructions, or tool output.

## Secrets

No host environment is inherited. Only `environment`, `security.allowed_environment`, and `security.allowed_secrets` values are injected.

**Important:** allowlisting a secret gives untrusted sandbox processes access to that value. ReproForge redacts known values from its reports, but redaction cannot prevent an attacker from encoding, transforming, or exfiltrating a secret before it reaches the reporter. Do not inject a credential unless it is necessary, narrowly scoped, short-lived, and its exposure to the target repository is acceptable.

## Network

`none` is the default. `bridge` is an explicit opt-in and is currently coarse-grained: `allowed_network_domains` is configuration metadata for a future domain-enforcing backend and does not create a Docker egress firewall today. Documentation and UI must not imply domain-level enforcement until it exists.

## Docker daemon

The host control plane invokes the Docker CLI. Containers never receive the Docker socket. Anyone who can control the ReproForge host process itself is outside this sandbox boundary because the host process already has permission to ask Docker to create containers.

## Supply-chain risks

Container image tags and language dependencies can change upstream. For high-assurance use, pin images by digest, use lockfiles, maintain trusted mirrors, and review build scripts. A lockfile reduces dependency ambiguity but does not make dependencies safe.

## Evidence integrity

Agent prose is never an oracle. Validation derives failure signals from independently executed commands. A malicious repository can still forge its own stdout, so high-confidence reproduction should prefer assertions, tests, compilers, protocol responses, and multiple deterministic reruns tied to the actual reported behavior.

## Out of scope for the initial Docker backend

- a kernel/VM boundary against a Docker/container escape vulnerability;
- domain-level egress filtering;
- hostile multi-tenant execution on the same daemon;
- protecting an explicitly injected secret from code in the sandbox;
- automatic semantic proof that a failing test exactly matches the user's issue.
